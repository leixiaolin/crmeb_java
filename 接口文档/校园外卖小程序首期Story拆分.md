# 校园外卖小程序 首期 Story 拆分

> 来源文档：`PRD-校园外卖小程序产品需求文档.md`  
> 拆分目标：将首期 MVP 范围拆为可独立排期、开发和验收的 Story。  
> 基线系统：CRMEB Java 商城系统二次开发。  
> 首期边界：仅交付微信小程序用户端、嵌入现有管理后台的商家端能力、运营后台能力；配送状态由后台人工更新。
> 完成情况：开发过程中以 `校园外卖小程序首期Story完成情况.md` 为断点记录；每完成一个 Story 或可验收子切片后必须同步更新。

## 1. 拆分原则

- Story 按用户价值和业务闭环拆分，不以接口、表结构或页面文件作为 Story。
- 每条 Story 都说明使用角色、业务目标、价值、验收标准和关键依赖。
- 首期 Story 覆盖正常链路、权限边界、金额规则和订单状态流转。
- 独立骑手端、第三方配送、多营业时段、优惠叠加、积分、余额、分销等二期能力不进入首期排期。

## 3. 基础业务底座

### BASE-01 学校、校区与宿舍楼基础数据管理

**用户故事**  
作为平台运营，我希望维护学校、校区、宿舍楼及启用状态，以便学生地址、配送规则和商家服务范围都有统一基础数据。

**验收标准**

1. 运营可新增、编辑、启用和停用学校、校区、宿舍楼基础数据。
2. 宿舍楼必须归属到可识别的学校或校区，停用项不再作为新地址和新订单的可选项。
3. 学生端选择地址时只展示当前可用的学校、校区和宿舍楼。
4. 已有订单保留下单时的地址快照，不因基础数据改名或停用而变化。

**依赖/备注**  
依赖校园地址模型和后台配置入口；多代理商管理若首期无明确运营规则，先保留学校/区域归属字段，不扩展结算逻辑。

### BASE-02 学生手机号认证与用户基础资料

**用户故事**  
作为学生，我希望通过微信手机号授权完成认证并维护基础资料，以便安全下单和接收履约联系。

**验收标准**

1. 未完成手机号认证的用户在下单前会被引导完成认证。
2. 微信授权成功后，系统记录用户手机号并可读取头像、昵称等基础资料。
3. 用户拒绝手机号授权时，不能进入需要手机号的下单流程，并得到明确提示。
4. 认证流程只面向微信小程序；首期不要求 H5、App、支付宝小程序兼容。

**依赖/备注**  
复用现有微信用户能力；手机号授权、隐私协议和小程序主体配置需要上线前联调。

### BASE-03 校园收货地址管理

**用户故事**  
作为学生，我希望维护学校、楼栋、楼层、宿舍号和联系人信息，以便下单时快速选择准确送达地址。

**验收标准**

1. 用户可新增、编辑、删除和设置默认校园收货地址。
2. 地址至少包含学校/校区、宿舍楼、楼层、宿舍号、联系人和联系电话。
3. 结算页可选择已保存地址，并在订单创建时保存地址快照。
4. 地址字段能支持按楼栋、楼层、宿舍号进行订单排序。

**依赖/备注**  
校园地址不直接复用普通商城省市区地址语义；需要和配送费楼层规则共享楼栋、楼层数据。

### BASE-04 多角色菜单权限与商家数据隔离

**用户故事**  
作为平台管理员，我希望为运营、客服、财务、商家和配送相关后台角色配置权限与数据范围，以便各角色只处理自己的业务。

**验收标准**

1. 平台管理员可访问首期全部外卖后台能力。
2. 商家账号仅能查看和操作自己店铺的商品、订单、退款、评价和统计。
3. 配送状态更新权限可单独分配给后台角色，首期不依赖独立骑手端。
4. 无权限账号不能通过页面按钮、接口参数或直接访问路由越权操作其他商家数据。

**依赖/备注**  
复用现有后台角色、菜单和权限体系；商家数据隔离是订单、退款、商品、评价和账单 Story 的前置约束。

## 4. 学生端浏览与选购

### BUY-01 小程序校园外卖首页

**用户故事**  
作为学生，我希望在首页选择校园地址并浏览分类、广告、推荐商家和活动入口，以便快速进入点餐。

**验收标准**

1. 首页包含地址入口、搜索入口、轮播广告、快捷分类、推荐商家和优惠活动入口。
2. 地址入口以手动选择或填写学校、楼栋、宿舍信息为主，不依赖自动定位。
3. 轮播广告、分类和活动展示内容可由运营配置。
4. 首页底部提供首页、外卖/美食、订单、我的四个首期入口。

**依赖/备注**  
复用现有小程序首页承载能力时，需要保证首期仅校验微信小程序端表现。

### BUY-02 商家与商品搜索

**用户故事**  
作为学生，我希望搜索商家和商品，以便在明确目标时快速找到可下单内容。

**验收标准**

1. 搜索词可匹配可用商家和可售商品。
2. 搜索结果能区分商家结果与商品归属商家。
3. 下线商家、下架商品和无权展示内容不会进入可下单结果。
4. 从搜索结果进入商家后，可继续加入购物车和下单。

**依赖/备注**  
搜索结果需受学校/区域、商家上线状态和商品审核状态约束。

### BUY-03 商家列表筛选与排序

**用户故事**  
作为学生，我希望按销量、评分、配送费、起送价和配送速度筛选或排序商家，以便找到适合当前需求的店铺。

**验收标准**

1. 商家列表卡片展示 logo、名称、评分、月售量、配送时间、配送费、起送价和优惠标签。
2. 列表支持 PRD 定义的筛选条件和综合、距离近、速度快三类排序入口。
3. 当前地址不可服务的商家不能被误导为可立即下单。
4. 首期未接入位置服务时，距离相关展示和排序必须使用可落地的学校/区域口径或明确降级口径。

**依赖/备注**  
PRD 明确首期不需要腾讯位置服务；距离口径需要在实现时和学校/区域配置保持一致。

### BUY-04 商家详情与商品分类浏览

**用户故事**  
作为学生，我希望查看商家营业信息、公告、商品分类和商品列表，以便决定购买内容。

**验收标准**

1. 商家详情展示营业时间、公告、评分和地址等商家信息。
2. 商品区提供左侧分类导航和右侧商品列表联动浏览。
3. 商品展示图片、名称、价格、库存和规格入口。
4. 非营业商家允许浏览，但不能完成提交订单。

**依赖/备注**  
首期营业设置为固定营业时间；多营业时段属于二期。

### BUY-05 商品规格选择与同店购物车

**用户故事**  
作为学生，我希望选择冷热、辣度、份量、套餐和加料等规格并加入购物车，以便按口味组合下单。

**验收标准**

1. 商品可根据配置展示多规格选择和价格变化。
2. 购物车支持加减商品、规格明细展示和金额合计。
3. 库存不足或商品下架后，不允许继续按失效数量结算。
4. 首期结算仅支持同一商家商品，不同商家商品不可合并为一个订单。

**依赖/备注**  
依赖商家商品规格和库存配置；多商家合并下单不进入首期。

### BUY-06 商家收藏、评价查看与客服入口

**用户故事**  
作为学生，我希望收藏商家、查看历史评价并联系商家客服，以便做购买决策和咨询问题。

**验收标准**

1. 已登录用户可收藏和取消收藏商家，并在后续找到收藏结果。
2. 商家详情可查看历史评价内容和商家回复。
3. 客服入口能进入首期定义的商家沟通入口。
4. 未配置客服渠道时，入口需要给出可理解的降级提示，而不是中断浏览链路。

**依赖/备注**  
在线沟通的具体承载方式沿用项目现有客服能力或首期配置结果。

## 5. 学生端下单与订单

### ORDER-01 结算页地址、商品和备注确认

**用户故事**  
作为学生，我希望在结算页确认地址、商品、餐具份数和备注，以便商家与配送人员按我的要求履约。

**验收标准**

1. 结算页展示所选地址、商品清单、数量、价格和预计优惠信息。
2. 用户可填写备注和餐具份数，并随订单提交。
3. 地址、商品、商家营业状态或库存失效时，系统阻止提交并提示原因。
4. 结算信息在创建订单前再次校验，不信任前端金额与库存数据。

**依赖/备注**  
依赖地址、购物车、商品库存和商家营业状态。

### ORDER-02 起送价与配送费试算

**用户故事**  
作为学生，我希望在结算前看到起送价、楼层配送费和雨天附加费，以便明确最终支付金额。

**验收标准**

1. 商品金额未达到平台配置起送价时，用户不能提交订单。
2. 配送费可根据宿舍楼和楼层规则计算并在结算页展示。
3. 雨天附加费开启后只影响新创建订单，并在金额明细中可见。
4. 订单实付金额、优惠金额、配送费和雨天附加费在前后端口径一致。

**依赖/备注**  
楼层配送费、雨天附加费、起送价配置见 `OPS-07`；配送费和优惠金额属于高风险测试点。

### ORDER-03 预约配送选择

**用户故事**  
作为学生，我希望按日期和时间段预约配送，以便订单在合适时间送达。

**验收标准**

1. 结算页支持选择可用日期与配送时间段。
2. 预约信息写入订单并在学生、商家和运营订单详情中可见。
3. 不可用时间段不能提交成功。
4. 首期只要求日期加时间段，不要求路线规划或精确预计送达时间。

**依赖/备注**  
需要和商家营业状态、配送履约口径一起确认可用时间段。

### ORDER-04 微信支付创建外卖订单

**用户故事**  
作为学生，我希望使用微信支付完成外卖订单付款，以便订单进入商家待接单流程。

**验收标准**

1. 首期支付方式只提供微信支付。
2. 支付成功后订单从待付款进入待接单，并可被商家和运营查看。
3. 支付失败、取消支付或回调异常时，订单状态与支付结果保持可追踪。
4. 支付金额使用服务端最终试算结果，不能被前端篡改。

**依赖/备注**  
微信小程序账号、支付商户号、证书、域名和回调配置是上线前置项。

### ORDER-05 外卖订单列表、详情与状态跟踪

**用户故事**  
作为学生，我希望查看外卖订单列表、详情和配送轨迹，以便知道订单当前进展。

**验收标准**

1. 订单列表可查看不同状态的外卖订单。
2. 订单详情展示商品、地址快照、金额明细、预约信息和当前状态。
3. 状态轨迹覆盖待付款、待接单、配送中、已送达、已完成、已取消、退款相关状态。
4. 首期骑手取餐、配送中和送达节点来源于后台人工更新，不要求骑手端上报。

**依赖/备注**  
订单状态流转应与外卖业务状态机一致，避免直接套用普通商城发货语义。

### ORDER-06 用户取消订单

**用户故事**  
作为学生，我希望在规则允许时取消订单，以便放弃错误或不再需要的订单。

**验收标准**

1. 待付款订单可取消且无需退款。
2. 已付款但商家接单前的订单可取消，并按规则原路退款。
3. 商家接单后的订单不提供用户主动取消入口。
4. 取消后库存、优惠和订单状态按退款及回滚规则保持一致。

**依赖/备注**  
依赖支付退款和库存回滚能力；取消按钮需要受状态控制。

### ORDER-07 用户发起退款申请

**用户故事**  
作为学生，我希望对符合规则的订单申请退款，并支持部分退款，以便处理履约问题。

**验收标准**

1. 用户可提交退款申请并看到退款处理中状态。
2. 退款申请可支持部分退款的业务入口和金额约束。
3. 商家处理后，学生可看到退款结果。
4. 不符合当前状态规则的退款请求会被拒绝并提示原因。

**依赖/备注**  
商家退款处理见 `MER-05`；配送费和雨天费的退款口径需要与支付退款规则一致。

### ORDER-08 再来一单与联系履约方

**用户故事**  
作为学生，我希望从历史订单再次购买并联系商家或骑手，以便快速复购和解决履约沟通问题。

**验收标准**

1. 历史订单可发起再来一单，仍需重新校验商品上下架、库存、价格和商家状态。
2. 订单详情提供联系商家入口。
3. 首期订单详情保留联系骑手入口或清晰的后台配送联系承载方式。
4. 联系入口不可绕过隐私和权限要求直接暴露不应公开的数据。

**依赖/备注**
