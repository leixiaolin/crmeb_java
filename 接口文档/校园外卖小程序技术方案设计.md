# 校园外卖小程序技术方案设计

## 1. 目标与边界

本文用于补充《校园外卖小程序 MVP 开发计划》中需要开发前明确的核心技术方案，重点解决以下风险：

- 外卖订单状态与现有商城订单状态语义冲突。
- 商家后台数据隔离不完整导致越权访问。
- 校园地址模型与现有收货地址模型不匹配。
- 配送费规则缺少可实现、可测试的计算口径。

首期仍限定为微信小程序用户端 + 现有 admin 内嵌商家/运营后台，不开发独立骑手端。

## 2. 订单状态机设计

### 2.1 订单类型隔离

新增订单类型字段，作为所有订单查询、定时任务、状态流转、统计、退款逻辑的分支依据：

- `order_type = 0`：普通商城订单，沿用现有逻辑。
- `order_type = 1`：校园外卖订单，走外卖状态机。

实现位置建议：

- 优先在现有 `StoreOrder` 增加 `orderType` 字段，便于所有订单任务和查询统一过滤。
- 同时新增外卖订单扩展表保存外卖专属字段，不把外卖字段堆入主订单表。

### 2.2 外卖扩展状态

外卖订单状态独立维护在扩展表中，避免强行复用商城“待发货/待收货”语义：

| 状态码 | 状态 | 说明 |
| --- | --- | --- |
| 0 | 待付款 | 已创建未支付 |
| 10 | 待接单 | 已支付，等待商家接单 |
| 20 | 配送中 | 商家已接单，进入配送履约 |
| 30 | 已送达 | 后台或骑手标记送达 |
| 40 | 已完成 | 用户确认或自动完成 |
| -10 | 已取消 | 付款前取消或接单前取消 |
| -20 | 退款中 | 用户或商家发起退款处理中 |
| -30 | 已退款 | 退款完成 |

主订单表保留支付、退款、完成等现有必要字段，但页面和业务判断以外卖扩展状态为准。

### 2.3 状态流转规则

- 待付款 -> 待接单：微信支付成功回调触发。
- 待付款 -> 已取消：用户主动取消或超时未支付自动取消。
- 待接单 -> 配送中：商家接单。
- 待接单 -> 已取消/已退款：用户取消或商家拒单，已支付时原路退款。
- 配送中 -> 已送达：后台人工更新配送状态。
- 已送达 -> 已完成：用户确认或自动完成任务触发。
- 任意可退款状态 -> 退款中 -> 已退款：按退款规则执行。

### 2.4 定时任务防误操作

所有现有订单定时任务必须增加 `order_type = 0` 过滤，避免误处理外卖订单：

- 自动取消未支付订单。
- 自动收货。
- 自动完成。
- 售后/退款相关定时任务。

外卖订单单独实现定时任务：

- 待付款超时取消：默认 15 分钟。
- 待接单超时提醒：默认 5 分钟提醒商家和运营。
- 待接单超时自动取消：默认 15 分钟，可后台配置。
- 已送达自动完成：默认 24 小时，可后台配置。

## 3. 数据隔离设计

### 3.1 商家数据归属

复用现有 `mer_id` 或等价商户标识，但开发前必须盘点外卖相关表是否具备商家归属字段：

- 商家资料、资质、商品、规格、库存。
- 购物车、订单、订单明细、退款、评价。
- 账单、提现、统计、打印配置。

凡是商家后台可查询或操作的数据表，必须具备 `mer_id` 或可稳定关联到 `mer_id` 的外键。

### 3.2 DataScope 拦截

新增统一数据范围能力，避免每个接口手写商家条件遗漏：

- 平台管理员：不限制商家数据。
- 运营/客服/财务：按角色权限访问对应模块数据。
- 商家账号：强制追加当前登录账号绑定的 `mer_id`。
- 骑手角色首期不开放独立端，只允许后台配送状态相关权限。

建议在 service/DAO 查询层增加 DataScope 注入能力；复杂统计 SQL 必须显式校验 `mer_id` 条件。

### 3.3 越权校验

所有写操作必须二次校验数据归属：

- 商家接单、拒单、商品上下架、库存维护、退款处理、评价回复。
- 请求参数中的订单 ID、商品 ID、退款 ID 不能直接信任，必须查询归属后再操作。

## 4. 地址模型设计

### 4.1 不改造现有 UserAddress 主结构

现有 `UserAddress` 面向普通商城省市区地址，不适合作为校园宿舍地址的主模型。首期采用新增外卖地址表：

- `id`
- `uid`
- `school_id`
- `campus_id`
- `building_id`
- `building_name`
- `floor_no`
- `room_no`
- `contact_name`
- `contact_phone`
- `is_default`
- `remark`
- `create_time`
- `update_time`
- `is_del`

### 4.2 学校与楼栋基础表

新增基础配置表：

- 学校表：学校名称、校区名称、启用状态、排序。
- 宿舍楼表：所属学校/校区、楼栋名称、最高楼层、排序、启用状态。
- 楼层配送费规则表：所属楼栋、楼层、基础配送费。

### 4.3 订单地址快照

创建订单时必须写入地址快照，避免用户后续修改地址影响历史订单：

- 学校名、校区名、楼栋名、楼层、宿舍号。
- 联系人、手机号。
- 当时适用的楼层配送费、雨天附加费。

## 5. 配送费规则设计

### 5.1 费用组成

配送费 = 楼层基础配送费 + 雨天附加费 - 会员卡减免。

订单实付 = 商品金额 - 优惠金额 + 配送费。

首期不支持多商家合并下单，因此不存在跨商家合并配送费计算。

### 5.2 楼层梯度费

每栋宿舍楼单独配置每层配送费，优先使用精确楼层配置：

- 若配置了该楼层费用，直接取该楼层费用。
- 若未配置该楼层费用，不允许下单，并提示“当前楼层未配置配送费”。
- 不在运行时自动推导费用，避免配置错误导致金额争议。

如后台需要批量生成梯度费用，按配置工具生成每层记录：

```text
fee(floor) = min_fee + (floor - min_floor) * step_fee
```

生成后仍落表为每层固定费用，订单只读取落表结果。

### 5.3 雨天附加费

雨天附加费由后台人工开关控制：

- 可按学校/校区配置开关。
- 可配置固定附加金额。
- 开启后新创建订单生效。
- 已创建订单不追补、不变更。
- 关闭后新创建订单不再收取。

### 5.4 起送价

首期起送价由平台统一配置：

- 按学校/校区配置统一起送价。
- 商品金额未达到起送价时不允许提交订单。
- 起送价判断不包含配送费。

### 5.5 会员卡减免

周卡/月卡首期只影响配送费：

- 可配置每天免配送次数或配送费折扣。
- 若使用免配送权益，配送费减免到 0。
- 雨天附加费默认不参与会员卡减免，除非后台配置允许减免。

## 6. 购物车与拆单策略

首期限制同店下单，不做多商家合并购物车：

- 购物车可保留多商家商品分组展示。
- 结算时只能选择一个商家的商品。
- 用户切换商家加购时提示“不同商家需分开下单”。
- 接口创建订单时校验所有商品属于同一商家，不满足则拒绝下单。

该策略减少支付、优惠、配送费、退款、商家接单和库存扣减复杂度。

## 7. 库存与营业规则

### 7.1 营业时间

首期每个商家只支持一个固定营业时间段：

- 用户端商家列表和详情展示营业状态。
- 非营业时间允许浏览，不允许提交订单。
- 已支付订单不因商家后续打烊自动取消。

### 7.2 库存扣减时点

采用支付成功后扣减库存：

- 创建待付款订单时锁定购物车价格快照，但不扣库存。
- 支付成功回调中扣减库存并进入待接单。
- 支付成功扣库存失败时，订单进入异常状态，由后台处理退款。
- 用户取消待付款订单不需要回滚库存。
- 接单前取消或商家拒单需要回滚库存。

### 7.3 每日库存

商品库存分为总库存与每日库存：

- 首期下单校验每日库存。
- 每日库存通过定时任务按商家配置重置。
- 未配置每日库存的商品按普通库存处理。

## 8. 通知与超时

### 8.1 新订单通知

商家新订单通知首期支持三类方式：

- admin 站内提醒。
- 微信小程序订阅消息。
- 飞鹅打印机自动打印小票。

短信通知作为可选能力，未配置短信服务时不阻塞订单。

### 8.2 超时规则

- 待付款 15 分钟未支付：自动取消。
- 待接单 5 分钟未处理：提醒商家和运营。
- 待接单 15 分钟未处理：自动取消并退款。
- 已送达 24 小时未确认：自动完成。

所有超时时长均需要后台配置项，以上为默认值。

## 9. 退款费用规则

### 9.1 配送费与雨天费退还

- 待接单取消或商家拒单：商品金额、配送费、雨天附加费全额退还。
- 配送中后用户不可主动取消；若售后退款，由商家处理。
- 部分退款默认只退商品金额，不退配送费和雨天附加费。
- 商家发起全额退款时，配送费和雨天附加费一并退还。

### 9.2 优惠与会员权益回滚

- 接单前取消或商家拒单：优惠券、会员配送权益、库存全部回滚。
- 配送中后售后退款：优惠券默认不退回，会员配送权益不退回。
- 部分退款按实际退款商品金额处理，不重新计算整单优惠。

## 10. 必须补充的开发前检查清单

- 盘点现有订单状态字段、定时任务和退款任务，确认所有普通商城任务加 `order_type = 0` 过滤。
- 盘点所有商家后台查询和统计 SQL，确认具备 `mer_id` 数据隔离。
- 设计外卖地址表、学校表、楼栋表、楼层配送费表、外卖订单扩展表。
- 明确同店下单限制，并在前端和后端同时校验。
- 明确微信支付、短信、飞鹅打印、订阅消息配置缺失时的降级行为。
- 建立订单状态机单元测试和配送费计算单元测试，作为首期后端验收门槛。
